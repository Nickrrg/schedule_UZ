# Конструктор расписания — архитектурное решение (ADR)

**Статус:** предложено · **Дата:** 2026-09-26 · **Относится к версии:** 0.6 → 1.x
**Связанные документы:** `ТЗ_этапы_разработки.md` (что делает система — функциональные требования и этапы), `ПМИ_конструктор_расписания.md` (испытания), `../README.md` (как читать код).
Этот документ отвечает на вопрос **«во что превращаем код и в каком порядке»** — с учётом шагов плана 2–7 (свой домен, аналитика, интеграция с eMaktab, подписка).

**Решения продукта (2026-09-26):**
- Интеграция с eMaktab **будет, но после пилота.**
- Сервер и хостинг — вопрос закрыт на стороне eMaktab, архитектура его не решает.
- Авторизацию eMaktab **в пилот не пробрасываем**, подключаем после пилота.

Отсюда два горизонта: **пилот** — без авторизации и без серверного хранения, но с моделью данных и портами, которые готовы к ним; **после пилота** — вход через eMaktab, серверное хранение, интеграция, подписка.

---

## 0. TL;DR

1. **Не переписываем с нуля и не делаем микросервисы.** Эволюционно выносим из одного HTML-файла **чистое ядро** (модель, правила учебного плана, справочники, движок, миграции) — без DOM и без знаний о платформе.
2. Всё, что зависит от окружения (хранилище, пользователь, аналитика, импорт/экспорт, подписка), прячем за **порты с подменяемыми адаптерами**. Переезд claude.ai → свой домен становится заменой адаптеров, а не переделкой кода.
3. **Модель данных сразу готовим к многошкольности:** UUID вместо счётчика `idSeq`, `schemaVersion` + цепочка миграций, `schoolId` (tenant) у рабочей области, `revision` для конкурентных сохранений, `externalRefs` для будущих ID eMaktab.
4. **Справочники (ЕСП, сетка КТП, приказы) — версионируемые пакеты данных**, отделённые от данных школы. Выход приказа — новая версия пакета, а не правка кода.
5. **Движок — чистая функция `solve(input) → result`** с JSON-контрактом. Сейчас работает в Web Worker, позже тот же контракт исполняет серверный решатель (CP-SAT) с мягкими ограничениями.
6. **Пилот — без авторизации:** данные в браузере (IndexedDB), анонимный `installId` для аналитики, экспорт/импорт JSON как страховка. **После пилота** — один сервис + PostgreSQL, вход через авторизацию eMaktab, `school_id` в каждой таблице и Row-Level Security; данные пилота «привязываются» к аккаунту без ручного переноса.
7. **Подписка и интеграция проверяются только на сервере.** Клиентская проверка обходится за минуту — платными делаем серверные возможности.

## 1. Контекст и ограничения

| Факт сейчас | Следствие |
|---|---|
| Один файл 196 КБ, ~2 800 строк, ES5, глобальный изменяемый `state`, ~100 функций | Работает, но каждая правка движка рискует сломать UI и наоборот; тестировать можно только «вырезая `<script>`» |
| Хранилище — `localStorage` + `db`/`user` платформы claude.ai | На своём домене разделение по людям/школам исчезает (README, «Хранение данных») |
| ID — `uid(prefix)` на счётчике `idSeq`, который хранится рядом с `state` | Два источника (локальный и облачный) могут выдать одинаковые ID; для маппинга на eMaktab и слияния данных непригодно |
| Нет `schemaVersion`; миграции — набор `ensure*()`/`migrate*()` по эвристикам | Каждая новая миграция увеличивает риск; невозможно понять, какой формат лежит в хранилище |
| Справочник ЕСП и `KTP_GRID` вшиты в код, копия справочника лежит в данных пользователя | Приказ №183 так и не перенесён: обновление нормативки = релиз кода + `ensureCatalog()` |
| Персональные данные: ФИО учителей | В пилоте не покидают браузер (кроме случаев, когда пользователь сам выгружает файл). Размещение сервера после пилота — на стороне eMaktab |
| Авторизации в пилоте нет | Данные разделены по браузеру, а не по человеку/школе. Для пилота это приемлемо; модель данных при этом уже содержит `schoolId`, чтобы после пилота не мигрировать |

**Противоречие в документах закрыто:** интеграция с eMaktab будет, после пилота. Утверждение ТЗ v0.6 «интеграция не планируется» устарело; ТЗ v0.6 заменён `ТЗ_этапы_разработки.md`.

## 2. Целевая архитектура

```
┌──────────────────────────── Клиент (браузер) ─────────────────────────────┐
│                                                                           │
│  app/ (UI)                                                                │
│   ├ views: 7 вкладок мастера, бот, расписание        ← только отображение │
│   ├ store: единый стор + команды (addClass, setHours…) + undo              │
│   └ i18n: один механизм, словари ru/uz(/qr)                                │
│           │ вызывает                                                      │
│  core/  (чистый TS, без DOM, без сети — работает в браузере, Node, Worker)│
│   ├ model      типы SchoolWorkspace, Class, Teacher…                      │
│   ├ migrations v1→v2→…→vN (строго по schemaVersion)                       │
│   ├ calendar   classDays/Shift/Periods, slotLayout                        │
│   ├ curriculum правила подстановки (ТЗ ФТ-6.2) поверх reference-пакета     │
│   ├ validate   предгенерационные проверки → список Issue{code,severity}   │
│   └ solver     solve(SolveInput) → SolveResult   (запускается в Worker)   │
│           │ через порты (интерфейсы)                                      │
│  ports/   Storage · Identity · Analytics · Importer · Exporter ·          │
│           Entitlements · SolverRuntime                                    │
│  adapters/ выбираются в composition root по окружению:                    │
│    claude.ai:  ClaudeDbStorage, ClaudeUser, BufferAnalytics               │
│    offline:    LocalStorage/IndexedDB, AnonymousIdentity                  │
│    eMaktab:    HttpStorage, EmaktabSsoIdentity, Metrika+BackendAnalytics, │
│                ApiEntitlements, RemoteSolver                              │
└───────────────────────────────────────┬───────────────────────────────────┘
                                        │ HTTPS, JSON
┌───────────────────────────────────────┴───────────────── Сервер (шаг 2–4) ┐
│  api (модульный монолит)                                                  │
│   ├ auth        OIDC с eMaktab SSO → user, school, role                   │
│   ├ workspace   GET/PUT рабочей области, оптимистичная блокировка         │
│   ├ schedules   версии расписания: draft → published (неизменяемые)       │
│   ├ solver      очередь задач, тот же core/solver или CP-SAT              │
│   ├ reference   пакеты справочников (ЕСП, КТП, приказы) с версиями        │
│   ├ events      приём событий аналитики                                   │
│   ├ integration/emaktab  anti-corruption layer: pull / push, маппинги ID  │
│   └ billing     вебхуки платёжного шлюза → entitlements                   │
│  PostgreSQL (school_id везде + RLS), хостинг в РУз                        │
└───────────────────────────────────────────────────────────────────────────┘
```

Ключевой принцип: **`core/` не знает, где он запущен.** Одинаковый код считает расписание в браузере, в тестах на Node и на сервере. Это то, что README уже называет «клиентская логика не привязана к платформе» — ADR закрепляет это структурно.

## 3. Решения

### ADR-1. Эволюция, а не переписывание (strangler)
**Решение.** Сохраняем работающий MVP. Ядро выносим модулями по одному, UI трогаем последним. Результат сборки на переходный период — **тот же один HTML-файл** (Vite + `vite-plugin-singlefile`), чтобы артефакт на claude.ai продолжал публиковаться без изменений.
**Почему.** Бизнес-логика (правила §6, ось слотов, групповые уроки) проверена на реальных данных 44 классов — переписывание её потеряет. Риск и стоимость — в UI-строках, а не в логике.
**Отклонено.** Переписать на React/Next с нуля — месяцы без ценности для пользователя, регрессии правил учебного плана.

### ADR-2. Стек: TypeScript + Vite; UI-фреймворк — отложенное решение
**Решение.** TypeScript (strict) для `core/` сразу — типы модели данных дают больше всего пользы именно там. UI сначала переносится как есть (функции `tpl*()` → модули). Когда дойдёт до переработки UI (роли, совместная работа, многонедельная сетка), брать **Preact + signals** (≈10 КБ, близко к текущему подходу «строка → DOM»), а не тяжёлый фреймворк.
**Отказ от ES5.** Целевые браузеры завучей — современные Chrome/Edge/Яндекс; ES2019+ собирается Vite без полифилов. Проверить по аналитике после подключения Метрики.

### ADR-3. Модель данных: документ рабочей области + версии расписания
**Решение.** Единица хранения — **рабочая область школы на учебный год** (`SchoolWorkspace`), один JSON-документ. Расписания — **отдельные сущности-версии**.

```ts
interface SchoolWorkspace {
  schemaVersion: number;          // строго растёт; миграции v(n)→v(n+1)
  id: UUID;
  schoolId: UUID;                 // tenant — с первого дня, даже если сейчас = id пользователя
  academicYear: "2026-2027";      // задел под многолетнюю историю и четверти
  revision: number;               // оптимистичная блокировка при сохранении
  reference: {                    // какой нормативный пакет применён
    catalog: "esp@1.10", ktp: "ktp@2026-order183"
  };
  config: { schoolType; parallels: Record<Grade, ParallelConfig> };
  classes: Class[]; subjects: Subject[]; teachers: Teacher[]; rooms: Room[];
  curriculum: Record<ClassId, Record<SubjectId, CurriculumEntry>>;
  constraints: ConstraintSpec[];  // задел под мягкие ограничения (ADR-5)
}
// у Class / Teacher / Subject / Room:
//   id: UUID; externalRefs?: { emaktab?: string; esp?: string; erp?: string }

interface ScheduleVersion {
  id: UUID; workspaceId: UUID; workspaceRevision: number;   // на каком плане построено
  status: "draft" | "published" | "archived";
  period: { from: Date; to: Date } | null;                  // задел под четверть/многонедельность
  grid: …; unplaced: …; solver: { engine: "greedy@1" | "cpsat@1"; seed; score };
  createdBy: UserId; createdAt;
}
```

**Почему документ, а не 10 нормализованных таблиц.** Движку всегда нужен весь набор данных; редактирует в основном один завуч; размер документа — сотни КБ. PostgreSQL `jsonb` + несколько индексируемых полей (`school_id`, `academic_year`, `revision`) проще и быстрее для этой задачи. Нормализуем то, что понадобится запрашивать поперёк школ (аналитика, биллинг) — это отдельные таблицы.

**Сразу (фаза 0), до любого бэкенда:**
- UUID (`crypto.randomUUID()`) вместо `idSeq` — миграция переписывает все ссылки (`curriculum`, `schedule`, `syncWith`, `teachers[].subjects`). Без этого нельзя ни слить локальные и облачные данные, ни связать с eMaktab.
- `schemaVersion` и явная цепочка миграций; нынешние `ensureParallels`/`migrateLegacySubjects`/`ensureCatalog` становятся миграциями v1…v4 с тестом на каждую.
- `schedule` выносится из `state` в отдельную сущность (в `localStorage` — отдельный ключ). Это готовит «черновик / опубликовано» для шага 6 (отдать расписание в eMaktab).

### ADR-4. Нормативные справочники — версионируемые пакеты данных
**Решение.** `REAL_SUBJECT_CATALOG`, `KTP_GRID`, `JASORAT_MAP`, `EKONOMIKA_MAP`, `TRACK_SUBJECT_VARIANTS` уходят из кода в JSON-пакеты `reference/esp/1.10.json`, `reference/ktp/2026-order183.json` со схемой и тестами. Рабочая область ссылается на версию пакета и хранит **только отличия** (предметы, добавленные школой; переопределения типа кабинета).
**Почему.** Приказ №183 не перенесён, «вариатив» ждёт правил, будут новые языки обучения — нормативка меняется чаще кода. `ensureCatalog()` «доливом по названию» ломается на переименованиях (уже пришлось писать `migrateLegacySubjects`). Связь по `espId`, а не по названию, решает это.
**Будущее.** На сервере пакеты раздаются через `/reference/{kind}/{version}`; обновление нормативки — публикация данных без релиза фронта. Школа видит «доступна новая сетка часов, применить?» с диффом.

### ADR-5. Движок: контракт `solve()`, Web Worker сейчас, серверный решатель потом
**Решение.**
```ts
solve(input: SolveInput, opts: { seed?; attempts?; timeLimitMs? }): SolveResult
// SolveInput — самодостаточный снимок: слоты, уроки (units), учителя, кабинеты,
//              заблокированные ячейки, constraints[]. Никаких обращений к state.
// SolveResult — сетка, unplaced[] с причинами, score, диагностика.
```
- Жёсткие ограничения (ТЗ ФТ-8.1) и **мягкие** (окна у учителя, «тяжёлые» не подряд, равномерность по неделе) описываются декларативно `ConstraintSpec { kind, params, hard | weight }`. Флаг `heavy` становится первым мягким ограничением.
- Порт `SolverRuntime`: `WorkerSolver` (текущий жадный алгоритм в Web Worker — UI не замерзает на больших школах), позже `RemoteSolver` (серверный CP-SAT/OR-Tools в очереди задач, с тем же контрактом).
- Результат несёт `engine` и `seed` — расписание воспроизводимо, можно сравнить движки на одних данных.
**Почему.** Конкурент (edarsjadval.uz) уже на OR-Tools; сравняться по качеству без мягких ограничений не получится, а переписывать UI под другой движок не нужно, если контракт зафиксирован сейчас. Серверный решатель — естественный кандидат в платную функцию (ADR-9).

### ADR-6. Хранение, идентичность, многошкольность
**Решение.**
- Порт `Storage { load(workspaceId), save(ws, expectedRevision), listSchedules… }`, порт `Identity { current(): { userId, schoolId, role } | anonymous }`.
- **Локальный кэш — IndexedDB** (а не `localStorage`: лимит ~5 МБ и синхронный API) с очередью несохранённых изменений: офлайн-работа сохраняется, при появлении сети — синхронизация с `revision`. При конфликте (сохраняли с двух устройств) — показать выбор, а не молча перезаписывать, как сейчас делает `initCloudSync()` («облако побеждает»).
- **Бэкенд:** авторизация **только через SSO eMaktab (OIDC)** — школа и роль приходят из eMaktab, своих паролей не заводим. Если SSO недоступен — вход по одноразовой ссылке/коду, но `schoolId` всё равно обязателен.
- **Роли:** `owner` (директор/админ школы), `editor` (завуч), `viewer` (учитель — смотрит своё расписание). Человек может состоять в нескольких школах.
- **Изоляция:** `school_id NOT NULL` в каждой таблице + PostgreSQL Row-Level Security по `current_setting('app.school_id')`. Проверка принадлежности — на уровне доступа к данным, не в UI (как и требовало ТЗ v0.6 для раздельной работы школ).
- **Аудит:** таблица `workspace_events` (кто, когда, какая команда) — нужна и для совместной работы двух завучей, и для аналитики активности.

Всё перечисленное выше — **после пилота**.

**Режим пилота (решение продукта: без авторизации и без серверного хранения).**
- Адаптеры: `IndexedDbStorage` (данные в браузере) + `AnonymousIdentity`. При первом запуске генерируются `installId` и `schoolId` (UUID) и сохраняются вместе с рабочей областью.
- В интерфейсе видна плашка «данные хранятся в этом браузере». Экспорт/импорт JSON — штатная страховка и способ перенести данные на другой компьютер. Импорт сохраняет `schoolId`, поэтому одна школа остаётся одной школой.
- Ограничение осознанное: два завуча за одним браузером видят общие данные. Для пилота это допустимо.
- **Переход после пилота без миграции:** при первом входе через eMaktab клиент предлагает «привязать данные из этого браузера к школе» — рабочая область с её `schoolId` и UUID-ами уходит на сервер как есть. Именно поэтому UUID, `schemaVersion` и `schoolId` вводятся уже в фазе 0.
- Внутри claude.ai по-прежнему работает `ClaudeDbStorage` — выбор адаптера автоматический.

### ADR-7. Аналитика: каталог событий + несколько приёмников
**Решение.** `track()` превращается в типизированный каталог событий (`events.ts`: имя, параметры, версия схемы) и порт `Analytics` с fan-out на приёмники: `BufferSink` (claude.ai, тесты), `MetrikaSink` (цели `tt_*`, как в ТЗ ФТ-13.1), `BackendSink` (`/events` → своя таблица). Идентификаторы — только псевдонимные (`schoolId`, `userId`), без ФИО/ПИНФЛ.
**Почему свой приёмник, а не только Метрика.** Вопросы «сколько школ реально составили и опубликовали расписание», «на каком шаге бросают» — это запросы по `school_id`, которых в Метрике нет. Своя таблица событий дешевле, чем спорить с ограничениями Метрики.
**В пилоте аналитика обязательна** (решение продукта). Состав событий и параметров уточняется у аналитика (ожидается в течение нескольких дней), поэтому архитектура строится так, чтобы ответ аналитика превращался в правку данных, а не в правку кода:
- **Каталог событий — один файл** (`contracts/events.ts`): имя, параметры, когда срабатывает. Вызовы в UI идут через `track(Event.X, params)`; добавить/переименовать событие — правка каталога и одной строки в месте вызова.
- **Общие параметры добавляются в одном месте** (обогатитель контекста): `installId`, `schoolId`, `lang`, `app_version`, а также будущие параметры школы — без изменения каждого вызова.
- **Приёмники независимы от каталога:** `MetrikaSink` (на своём домене Метрика загрузится), `BufferSink` (claude.ai, тесты, отладка — `window.__ttEvents`). `BackendSink` — после пилота.
- Что можно делать **до ответа аналитика:** порт `Analytics`, каталог с текущими событиями из ТЗ ФТ-13.1, `installId`/`schoolId`, тест «каждое событие из каталога где-то вызывается, и в параметрах нет ФИО/ПИНФЛ».
- Разбивка по школам без авторизации возможна только если пользователь сам укажет школу (например, необязательное поле «школа, район» в первом шаге мастера, или код школы из ссылки-рекламы в eMaktab — `?school=…`). Какой вариант — зависит от ответа аналитика.

**Вопросы к аналитику** (чтобы ответ сразу ложился в каталог):
1. Какие метрики пилота считаются успехом (сколько школ, сколько составили расписание, сколько выгрузили)?
2. Что считать «активным использованием» (предложение ниже)?
3. Нужна ли разбивка по школам/районам/регионам, и откуда брать школу: спрашивать у пользователя или передавать в ссылке из eMaktab?
4. Какие шаги воронки нужны и с какими параметрами?
5. Только Метрика, или события нужно дублировать ещё куда-то?
**Предложение к аналитику** (закрыть открытый вопрос из README): «активная школа за неделю» = хотя бы одно из `schedule_generate` / `schedule_publish` / `export_*`; «вовлечённый завуч» = ≥3 сессии с изменением данных. Воронка: `open → classes_done → curriculum_done → generate → export|publish`.

### ADR-8. Интеграция с eMaktab: слой-переводчик на сервере
**Сроки:** после пилота. В пилоте из этого ADR нужно только то, что закладывается в модель: `externalRefs` у сущностей, `espId`/`erpId` у предметов, отдельные версии расписания со статусом `published`.
**Решение.** Модуль `integration/emaktab` на сервере (браузер не ходит в API eMaktab напрямую):
- **Pull:** учителя, классы, кабинеты, предметы → **черновик изменений с диффом**, который завуч подтверждает. Никогда не перезаписывать рабочую область молча.
- **Маппинги:** таблица `external_refs(school_id, entity, internal_id, system, external_id)`; для предметов — ключ `espId`/`erpId`, для «Технология: мальчики/девочки» (нет ID ЕСП) — явный ручной маппинг.
- **Push:** отдаём только **опубликованную неизменяемую версию** расписания (`ScheduleVersion.status = published`), идемпотентно по `version.id`.
- Нынешний `parseStaffExport` остаётся адаптером `FileImporter` за тем же портом `Importer` — ручная загрузка работает и без API.

### ADR-9. Подписка: права (entitlements), а не проверки в коде
**Решение.** Сервис `billing` принимает вебхуки платёжного шлюза (для РУз: Payme / Click / Uzum — выбор за продуктом) и пишет `entitlements(school_id, plan, features[], limits, valid_until)`. Клиент получает права через порт `Entitlements` и только **отображает** ограничения. Реальный контроль — на сервере, на серверных возможностях: облачное хранение и совместная работа, интеграция с eMaktab, серверный решатель, история версий, PDF.
**Почему.** Ядро выполняется в браузере — любую клиентскую блокировку снимают через DevTools. Биллинг не должен проникать в `core/`.

### ADR-10. Локализация: один механизм
**Решение.** Три механизма (`t`/`bt`/`uzt`) сводятся к одному: `t(key, params)` + словари `i18n/ru.json`, `i18n/uz.json` (позже `qr.json` — каракалпакский, язык обучения уже есть в модели). `uzt("русская строка")` заменяется скриптом-кодмодом на ключи. Названия предметов по-прежнему из reference-пакета (`nameUz`). В CI — проверка «все ключи переведены» и «в uz-рендере нет кириллицы» (сейчас это делалось вручную).

### ADR-11. Качество: репозиторий, тесты, CI
**Решение.**
- Локальная папка не под git, хотя репозиторий `Nickrrg/schedule_UZ` существует — первым делом синхронизировать, файлы без суффиксов `(7)`, `(1)`.
- **Vitest** для `core/`: миграции на каждую версию схемы, правила учебного плана (таблично), движок — **инварианты** (нет двойных назначений учителя/класса/кабинета; групповые уроки в одном слоте; блоки подряд) + **golden-фикстуры** на обезличенных реальных данных (44 класса).
- **Playwright** — один сквозной сценарий UI в RU и UZ.
- GitHub Actions: typecheck → тесты → сборка single-file HTML → артефакт.
- Всё, что раньше жило в scratch-скриптах (`tests/README.md`), становится этим набором.

## 6. Что сознательно НЕ делаем

- Микросервисы, Kubernetes, event sourcing — один сервис + Postgres покрывают масштаб «все школы РУз» (≈10 тыс. школ, документ ≈ сотни КБ, пиковая нагрузка — август).
- Нормализация всей модели в таблицы — пока нет запросов поперёк школ к её содержимому.
- Собственная система логинов и паролей — только SSO eMaktab.
- Проверки подписки в клиентском коде как средство защиты.
- Real-time совместное редактирование (CRDT) — хватит `revision` + «кто сейчас редактирует». Вернуться, если аналитика покажет, что два завуча реально правят одновременно.
