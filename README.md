# schedule_UZ — README для разработчика

Конструктор расписания для школ Узбекистана: загрузка текущего расписания из eMaktab и его проверка, классы, предметы, учителя, кабинеты, учебный план по приказам, автогенерация, выгрузка в Excel и печать. **Этот README — как запустить и как читать код.** Всё остальное — в `docs/` (оглавление — `docs/README.md`).

## Статус

Текущая версия — **0.11.0** (в работе, не зафиксирована): правила школы (вопросы «да / нет»: «Kelajak soati» Пн-1, математика 1–4 первым уроком, дни профессионального развития), закрытые уроки учителей, перенос изменений в eMaktab, базовый учебный план 2026–2027 (приказ №133, в т.ч. 1–4 классы), фокус на старте (`CHANGELOG.md`). Последняя зафиксированная — 0.10.0 (`_релизы/v0.10.0/`): загрузка из eMaktab и проверка. Дальше — перестроение с минимумом изменений и флоу четверти (`docs/План_доработок.md`, дорожная карта).

**Продолжение работы — начинать с `docs/Пилот_импорт_eMaktab.md`, раздел 9.** Папка `дано/` содержит реальные данные школ (ФИО) — **не загружать на GitHub**.

## Как запустить

Открыть `index.html` в браузере. Сборки, зависимостей, сервера — нет. Один файл: HTML + CSS + весь JS в одном `<script>`, без фреймворка, синтаксис ES5-совместимый.

Единственная внешняя зависимость — `xlsx-js-style` 1.2.0 с cdn.jsdelivr.net (SheetJS 0.18.5 с записью стилей): чтение выгрузок eMaktab и выгрузка Excel. Всё остальное работает офлайн.

## Порядок чтения файла

Внутри `<script>` всё идёт последовательно, в этом порядке имеет смысл читать:

1. **Справочники и данные** — `REAL_SUBJECT_CATALOG` (126 предметов ЕСП, у каждого `name`/`nameUz`), `KTP_GRID` (официальная сетка часов), `JASORAT_MAP` / `EKONOMIKA_MAP` / `TRACK_SUBJECT_VARIANTS` (правила подмены варианта предмета)
2. **`STRINGS`, `BOT_T`, `t()`, `bt()`, `uzt()`, `UZ_TR`** — локализация. Три отдельных механизма, не путать (см. ниже)
3. **`defaultState()` / `ensureParallels()` / `ensureCatalog()` / `migrateLegacySubjects()`** — форма `state` и миграции старых сохранений при загрузке
4. **`classDays()` / `classStart()` / `classPeriods()` / `slotLayout()`** — как для конкретного класса считаются дни, первый урок (сквозная нумерация школы, как в eMaktab) и уроки в день, и как из этого строится общая ось слотов школы (слот = номер урока школы − 1)
5. **`tpl*()` функции** — рендер шагов мастера (`tplClasses`, `tplLoad` — нагрузка параллели и `tplCurriculum` — план класса, `tplSchedule`, `tplExport`) и «Справочников» (`tplRefs` → `tplTeachers`, `tplSubjects`, `tplRooms`); строки HTML через конкатенацию, без шаблонизатора. Готовность шагов для степпера — `stepStatus()`
6. **`computeUnits()` / `tryBuildOnce()` / `generateSchedule()`** — движок расстановки
7. **Бот** (`botScreen()`, `botImportScreen()`, `renderBot()`) — первый вопрос «Расписание уже есть в eMaktab?»: загрузка и итог проверки или 5 экранов-анкет с нуля; путь и шаг хранятся в `localStorage` (`tt_bot`)
7а. **Загрузка из eMaktab** (`emkDetect()`, `emkParseGrid()`, `emkParseLoad()`, `emkBuild()`, `emkApply()`), **сверка с планом** (`planDiff()`, `suggestDirection()`) и **проверка расписания** (`checkSchedule()`, `checkCardHtml()`) — блоки перед выгрузкой Excel; устройство — `docs/Техническое_описание.md`, раздел 4
8. **`initCloudSync()` / `saveState()`** — хранение (см. «Хранение данных» ниже)
9. **`onClick()` / `onChange()`** — единый обработчик действий интерфейса, диспетчеризация по `data-act`
10. **Инициализация в самом низу файла** — `render(); initCloudSync();`

## Модель данных

Одна переменная `state`, схема 3 целиком — `docs/Техническое_описание.md`, раздел 3. Коротко: `config` (только `schoolType` + `parallels[1..11]` с днями/первым уроком (`start`)/уроками по умолчанию, `schoolBells`), `classes`, `subjects`, `teachers`, `rooms`, `curriculum`, `schedule`, `emaktab` (сведения о загрузке из eMaktab, сопоставление предметов, снимок исходной сетки); у загруженных учителей, классов, кабинетов и строк плана — `ext` с именем из eMaktab. У класса любой из трёх параметров параллели (`daysOverride`/`startOverride`/`periodsOverride`) можно переопределить — везде одно и то же правило: **значение класса → значение параллели → запасное значение**.

## Три механизма локализации — не путать

- **`t(key)` + `STRINGS`** — статичные подписи интерфейса (кнопки, заголовки, шапка).
- **`bt(key, vars)` + `BOT_T`** — реплики бота. Отдельный словарь, потому что реплики параметризуются (`{n}`, `{g}`) и не пересекаются со `STRINGS`.
- **`uzt(ru)` + `UZ_TR`** — единственный механизм, где ключ — сама русская строка, а не условное имя. Использован там, где строка вморожена прямо в HTML-разметку в `tpl*()` и заводить для неё отдельный ключ было бы избыточно. **Если добавляете новую русскую строку в разметку — либо оборачивайте в `uzt("...")` и дописывайте перевод в `UZ_TR`, либо (если строка регулярная и переиспользуется) заведите ключ в `STRINGS`.** Названия предметов переводятся отдельно, третьим путём — через `nameUz` у самого предмета (см. `subjectName()` / `subjDisplay()`).

Слова с `oʻ`/`gʻ`/`ʼ` — это не апострофы с клавиатуры, а модификаторные буквы узбекской латиницы (U+02BB, U+02BC). Если правите узбекский текст руками, используйте `uzNorm()` вместо ручного набора, иначе тест на дубли/консистентность может не пройти.

## Хранение данных

- `localStorage` — работает всегда и везде, это резервный слой. С 0.8: `saveState()` пишет, только если данные изменились; ошибка записи — плашка `#storageBar`; нечитаемое сохранение откладывается в `timetable_builder_v4_corrupt`; при открытии второй вкладки прежняя становится «только для чтения» (`initTabGuard()`, ключ `timetable_builder_tab`).
- Расписание при правках не стирается: вместо `state.schedule = null` вызывается `invalidateSchedule(причина)` — пометка «устарело» и `sanitizeSchedule()` (убирает только невозможные ячейки). Новые правки данных, влияющие на расписание, должны вызывать именно его.
- `db` + `user` (capability платформы claude.ai) — данные каждого залогиненного пользователя в `data/users/<id>/state`, недоступны другим зрителям той же страницы. **Работает только внутри claude.ai.**
- **На своём домене (eMaktab) `db`/`user` вернутся пустыми, и код молча откатится на `localStorage`.** Это осознанный fallback (см. `initCloudSync()`), не баг — но при переезде на свой домен разделение данных по человеку/школе пропадает целиком, остаётся только разделение по браузеру. Если несколько человек работают за одним компьютером в одном браузере — данные общие. Это прямо связано с шагом 5 плана: без своего бэкенда с настоящей авторизацией многопользовательская школа не решается в принципе, `localStorage` для этого не инструмент.

## Тестирование

**Перед каждой выкладкой:** открыть `tests/browser/smoke.html` через локальный сервер (`py tools/npa/devserver.py`, адрес `http://localhost:8766/tests/browser/smoke.html`; или любой статический, например `py -m http.server 8767`) и нажать «Запустить» — все проверки должны быть PASS (168 на 0.10.0). Сценарии загрузки eMaktab читают обезличенные выгрузки из `tests/fixtures/emaktab/`. Данные приказов в `index.html` не правятся руками — только `py tools/npa/build_plans.py --inject index.html` (см. `tools/npa/README.md`).

Тестов в CI нет, но подход, которым правился код весь этот проект, — в `tests/README.md`: код страницы запускается в Node.js на заглушке DOM (без браузера), после чего тестовые функции вызывают `tplClasses()`, `generateSchedule()` и т.д. напрямую и проверяют результат. Там же — список того, что проверялось на каждую крупную правку (per-class дни/смены/уроки, групповые уроки, кабинеты, дробные часы, полный проход бота, 100% узбекской локализации, миграция старых сохранений). Сами скрипты не включены — они писались по одному под конкретную правку в scratch-окружении и не оформлены как переиспользуемый набор. Дальнейшая работа должна класть новые сценарии в `tests/`, а не терять их между правками, как это было раньше.

## Аналитика (п.4 плана)

Слой `track(goal, params)` работает через каталог `EVENT_CATALOG` (с 0.8): событие вне каталога не отправляется, параметры вне списка отбрасываются, строковые значения — только коды (так ФИО и названия не попадают в аналитику). Новое событие = строка в каталоге + вызов. Ко всем событиям добавляются `install_id` и `school` (из `?school=`). Вехи воронки — `milestone()` / `checkMilestones()`. Список событий и то, чего не хватает для реального счётчика (номер счётчика, домен, согласие на JS-цели) — в `docs/ТЗ_этапы_разработки.md`, ФТ-13, и `docs/ARCHITECTURE.md`, ADR-7. **Что стоит уточнить у аналитика до реализации:** что считать «активным использованием» (открыл вкладку / нажал «Сгенерировать» / реально скачал файл), нужна ли разбивка по школам без явной регистрации пользователя (см. пункт про хранение выше — без нормального логина это будет приблизительно, по браузеру), и на каких именно шагах воронки нужны события — сейчас список событий сделан по моему усмотрению (открытие вкладки, шаги бота, генерация, экспорт), а не по согласованной воронке.

## Куда это не дотягивает без переделки (архитектура на будущее)

Клиентская логика (движок, правила учебного плана, справочники) не привязана к платформе и может быть перенесена как есть. Не переживёт «просто перенос»:

- **Хранение** — см. выше. Для многопользовательской школы и для разделения по школам (не по браузеру) нужен свой бэкенд с авторизацией и tenant ID у каждой записи с первого дня схемы, не добавленным потом.
- **Интеграция с eMaktab** (шаги 5–6 плана) — забрать учителей/предметы/кабинеты, отдать составленное расписание обратно. Внутренний API eMaktab нельзя дёргать напрямую из браузера — нужен сервер-посредник. Реализовано сейчас: только чтение одного конкретного отчёта «Сотрудники» через ручную загрузку файла (`parseStaffExport`), это не то же самое, что API-интеграция.
- **Подписка** (шаг 7) — платёжный шлюз, привязка оплаты к школе или человеку, проверка доступа при каждом открытии.

Архитектура под эти три пункта описана в `docs/ARCHITECTURE.md` (ADR-6 — хранение и разграничение школ, ADR-8 — интеграция, ADR-9 — подписка) — свериться с ним перед началом работы над бэкендом.
