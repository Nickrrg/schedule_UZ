# Конструктор расписания — архитектура и техническое задание

**Репозиторий:** https://github.com/Nickrrg/schedule_UZ
**Текущая реализация:** `timetable-builder.html` — веб-прототип, один самодостаточный файл.

## 1. Назначение

Инструмент для завуча: собрать данные о школе (классы, предметы, учителя, кабинеты, учебный план) и автоматически сгенерировать бесконфликтное расписание уроков, с ручной правкой и экспортом в Excel.

Ключевое отличие от существующих на рынке решений (ProRector — десктоп, символическая цена, но результат вручную переносится в eMaktab; edarsjadval.uz — веб, сильный движок на Google OR-Tools, готовит прямую интеграцию с eMaktab): этот инструмент рассчитан на использование **внутри** экосистемы eMaktab, без выгрузки данных на сторону. Интеграция с eMaktab отсутствует принципиально и не планируется — осознанное решение продукта, не техническое ограничение.

## 2. Технологическая архитектура (текущая)

| Слой | Решение |
|---|---|
| Исполнение | Один HTML-файл, ванильный JS (ES5-совместимый синтаксис), без сборки и без фреймворка |
| Хранение | `localStorage` браузера (ключ `timetable_builder_v4`) — данные не покидают устройство завуча |
| Экспорт в Excel | SheetJS (`xlsx.full.min.js`, CDN cdnjs) |
| Экспорт файлов / загрузка | опубликованная веб-страница (Artifact) с capability `downloads`; при недоступности — fallback через `Blob`+`<a download>` |
| Импорт данных | Разбор HTML-таблицы отчёта «Сотрудники» из eMaktab (файл `.xls`, фактически HTML) через `DOMParser` |
| Вёрстка/стиль | Чистый CSS, без Tailwind/Bootstrap; тема — светлая/тёмная/системная |

Никакого бэкенда нет. Всё состояние — один JS-объект `state`, сериализуемый в JSON. Ровно поэтому сейчас **не стоит** вопрос разграничения данных между школами: у каждого завуча — свой браузер, свой `localStorage`, данные физически не могут пересечься. Это перестаёт быть верным в тот момент, когда появится любое общее хранилище (см. раздел 9).

## 3. Модель данных (`state`)

```
state = {
  config: {
    days: 5|6,                      // дней в неделе — значение по умолчанию для школы
    shifts: 1|2,
    periodsPerShift: number,
    homeschoolPeriodsPerDay: number, // уроков в день для классов на домашнем обучении
    schoolType: "criterial"|"classical"
  },
  classes: [{
    id, name, shift,
    daysOverride: 5|6|null,          // переопределение дней недели для конкретного класса
    isHomeschool: boolean,           // домашнее обучение — свой диапазон периодов после обеих смен
    grade: 1..11|null,
    studentCount: number|null,
    instructionLang: "uz"|"ru"|"qr",
    jasorat: boolean,                // направление "Жасорат", 5-6 класс
    track: "none"|"mf"|"kb"|"oc"|"mc"|"ix"|"nd1"|"nd2",  // профиль, 10-11 класс
    trackLang: "uz"|"ru"|"qr",
    firstForeignLang, secondForeignLang,
    technologyMode: "split"|"unified"|"agro",
    officialPlanApplied: boolean
  }],
  subjects: [{ id, name, espId, erpId, roomType: string|null, heavy: boolean }],
  teachers: [{ id, name, subjects:[subjId], maxPerDay, daysOff:[bool x 6], homeroomNote? }],
  rooms: [{ id, name, capacity, type: string|null }],
  curriculum: {
    [classId]: {
      [subjectId]: {
        hours,                      // может быть дробным (0.5, 1.5...)
        teacherId: id|null,         // null — урок без назначенного учителя, это легитимный случай
        unofficial: boolean,
        blockSize: 1|2|3,
        syncWith: subjectId|null    // групповой урок — связь с другим предметом того же класса
      }
    }
  },
  schedule: {
    byClass: { [classId]: [day][period] -> { lessons:[{subjectId,teacherId,roomId}], locked } | null },
    unplaced: [{classId, subjectId, teacherId}],
    unplacedCount
  }
}
```

Слот времени — единая числовая ось на весь день: `classPeriodInfo(cls)` даёт `{offset, periodsPerDay}` для конкретного класса (обычная смена или домашнее обучение), `classDays(cls)` — число дней в неделе для конкретного класса (с учётом `daysOverride`). Сетки занятости учителей и кабинетов (`teacherBusy`, `roomBusy`) всегда считаются на максимум 6 дней и на все слоты школы разом (`totalSlotsPerDay()` включает обе смены + диапазон ДО) — это то, что делает конфликт между 5-дневным и 6-дневным классом, между обычным классом и «виртуальным» классом ДО, физически обнаружимым.

### 4.1 Правило подстановки часов (`computeOfficialPlan`)

1. Официальные цифры доступны только если `schoolType==="criterial"` и класс 5–11.
2. Без профиля — берётся колонка `base` по номеру класса.
3. Профиль 10-11 класса — колонка трека **полностью заменяет** базовую (не складывается с ней).
4. Название предмета подменяется на вариант ЕСП («по выбору» / «Экономика» / «Жасорат»), но **только если часы трека отличаются от обычных для этого же класса**. Направление роста часов определяет вариант: больше обычного → «по выбору», меньше — «Экономика».
5. «Жасорат» (5-6 класс) — предметный набор реальный (из ЕСП), но часы официально не описаны нигде: берутся как в обычной сетке, с явной пометкой «часы не официальные».
6. Взаимоисключающие альтернативы (родной язык по языку обучения, выбор 1-го/2-го иностранного, разбивка «Технологии» на группы) помечены в `KTP_GRID` полями `langGroup` / `choiceGroup` / `techVariant` и фильтруются по параметрам класса.

## 5. Функциональные модули (вкладки)

1. **Классы и смены** — параметры недели по умолчанию + тип школы; на класс — переопределение дней недели, флаг «домашнее обучение», параллель, число учеников, язык обучения, специализация (Жасорат/трек).
2. **Предметы** — общий справочник (126 предметов из ЕСП), у каждого: обязательный тип кабинета и флаг «тяжёлый» (задел под будущую мягкую оптимизацию, пока не используется движком).
3. **Учителя** — вручную или импортом реального отчёта eMaktab; предметы, макс. уроков/день, выходные дни (6 дней, на всякий случай, даже если школа по умолчанию на 5-дневке).
4. **Кабинеты** — название, вместимость, тип.
5. **Учебный план** — автозаполнение из `KTP_GRID` для критериальной школы 5–11 класса, ручной режим для остального. На уровне предмета: часы (можно дробные), блок (обычный/сдвоенный/строенный), связь с другим предметом для группового урока (плюс кнопка «Разделить на 2 группы», которая заводит вторую группу и связку одним кликом), учитель может быть не выбран (легитимно).
6. **Расписание** — генерация, ручная правка ячейки, блокировка ячейки (сохраняется между перегенерациями), просмотр по классу и по учителю, таблица соответствия часов плану (с учётом округления дробных часов).
7. **Экспорт** — Excel (по листу на класс + на учителя + сводный по кабинетам), JSON-бэкап настроек школы, сброс.

## 6. Движок генерации расписания

Жёсткие ограничения (модель по образцу edarsjadval.uz — без их OR-Tools, реализовано как рандомизированный жадный алгоритм с несколькими попытками):

- **Конфликты** — учитель/класс/кабинет не в двух местах одновременно (сетки занятости общие на всю школу и все диапазоны периодов, включая ДО).
- **Вместимость и тип кабинета** — предмет с заданным `roomType` ищет кабинет этого типа и вместимости; без заведённых кабинетов проверка отключается целиком.
- **Групповые уроки** (`syncWith`) — два предмета одного класса, связанные друг с другом, всегда ставятся в один и тот же слот, разными учителями.
- **Сдвоенные/строенные уроки** (`blockSize`) — блок из 2-3 уроков подряд в один день.
- **Дробные часы** — округляются вверх до целого слота при расстановке (`Math.ceil`), исходное дробное значение сохраняется для отчётности и явно помечается в интерфейсе.
- **Урок без учителя** — размещается как обычный урок класса, но не участвует в проверке занятости учителя (нечего проверять).
- **Домашнее обучение** — свой диапазон периодов после обеих смен, свой (обычно меньший) счётчик уроков в день.
- **Дни недели по классу** — конкретный класс может быть короче школьного значения по умолчанию (обычно 1-4 класс на 5-дневке при 6-дневной школе).
- **Блокировка ячейки** — при повторной генерации заблокированные уроки не трогаются.

Алгоритм (`tryBuildOnce`): для каждого класса строится список «юнитов» (`computeUnits`), сортируется по убыванию часов, распределяется по дням (балансировка нагрузки) и слотам со случайным перебором; 40 попыток с разными seed, выбирается лучшая по числу неразмещённых уроков.

**Предгенерационная проверка (`validateBeforeGenerate`):** пустой план, несовпадение часов в групповой паре, отсутствие кабинета нужного типа, превышение недельной нагрузки учителя. Отсутствие учителя у предмета — **больше не блокирует** генерацию (легитимный реальный случай, см. раздел 7).

## 7. Сверка с реальным расписанием школы — что подтвердилось

Проверено на реальных выгрузках eMaktab: 44 класса, 1-11 параллель, полная неделя каждого класса, плюс отдельно выгрузка на четверть по одной параллели (10 недель).

**Подтвердило правильность архитектуры:**
- Групповые уроки с разными учителями — реальный и частый паттерн, не только у «Технологии» (языки, информатика, физкультура тоже делятся на 2 группы) → механизм `syncWith` сделан общим, не частным случаем.
- Найдено 9 настоящих двойных назначений учителя в реальном расписании школы (один учитель одновременно в двух разных классах) — подтверждает практическую ценность конфликт-чекера.
- Найден паттерн «один и тот же учитель в обеих группах одного разделённого предмета» (14 раз на выборке) — по итогам решили считать это не багом нашей модели, а вопросом к тому, как реальная школа ведёт журнал; `syncWith` по-прежнему требует двух разных учителей.

**Привело к доработкам (уже сделано):**
- Разная длина недели по параллели (1-4 класс — 5 дней, 5-11 — 6) → `daysOverride` на классе.
- Домашнее обучение — свой диапазон периодов, отдельный от обеих смен → `isHomeschool` + `homeschoolPeriodsPerDay`.
- Реальные пустые слоты «нет учителя» → `teacherId: null` — легитимное состояние, не ошибка ввода.
- Официальные планы (приказ №183) содержат дробные часы (0,5ч и т.п.) → округление вверх при расстановке с пометкой в интерфейсе.

**Осталось под вопросом, не встроено:**
- Выгрузка на четверть показала, что расписание в eMaktab — это последовательность **отдельных недель** на всю четверть (10 недель, каждая со своей датой), а не одна повторяющаяся неделя. У проверенной школы недели 6-9 были заметно скуднее заполнены — рабочая гипотеза «завуч не успел доделать вперёд», а не системная особенность. Полноценная многонедельная сетка **не строится** до дополнительного подтверждения.

## 8. Явные упрощения и известные ограничения

- **Нет мягкой педагогической оптимизации** — 8 критериев конкурента (нет «окна» у класса, распределение предмета по неделе, дистанция между повторами, отсутствие соседних одинаковых уроков, баланс дневной нагрузки, тяжёлые предметы не подряд, окна учителя, усталость/выходной) не реализованы; движок жадный, а не оптимизирующий. Поле `subject.heavy` заведено, но пока никем не используется.
- **Preflight-диагностика** заметно проще, чем «28 типов проблем» у конкурента.
- **Нет PDF-экспорта** — только Excel.
- **«Технология: мальчики/девочки»** — два предмета-заглушки без единого ID ЕСП; в реальном справочнике это один и тот же предмет «Технология» — для интеграции с ЕРП может потребоваться доп. маппинг.
- **Категория предметов «вариатив»** (справочник ЕСП, версия 1.10) заведена в каталог, но не встроена в автозаполнение — неясно, к какому классу/треку относится.
- **Приказ №183** (см. раздел 4) даёт более точные и полные данные по 10-11 классу, чем `Sxema_KTP.xlsx`, включая 2 дополнительных языка обучения («братские», два варианта состава) — `KTP_GRID` пока не переведён на этот источник.
- **Многонедельная сетка на четверть** — см. раздел 7, отложено до уточнения.
- **Дизайн интерфейса** — намечена смена визуального стиля, работа не начата на момент этой редакции документа.

## 9. Что заложить в архитектуру на будущее

Ничего из этого не реализовано сейчас — раздел фиксирует требования, которые должны определить архитектуру, если/когда инструмент будет развиваться дальше.

### 9.1 Два языка интерфейса — русский и узбекский
Сейчас весь интерфейс (подписи, кнопки, подсказки) — захардкоженные русские строки прямо в HTML/JS-коде. Для двуязычности потребуется:
- Вынести все строки интерфейса в отдельный словарь (ключ → перевод), а не хранить их внутри разметки.
- Переключатель языка интерфейса должен быть независим от `instructionLang` класса (язык обучения) и от языка данных (названия предметов остаются как в справочнике ЕСП — на русском/узбекском, как они заведены, это отдельный вопрос от перевода самого интерфейса).

### 9.2 Разграничение данных между школами (многопользовательность)
Требование сформулировано жёстко: **два завуча из разных школ должны работать полностью раздельно, без единой точки пересечения данных.**

Сейчас это обеспечено «бесплатно» — инструмент клиентский, у каждого пользователя свой браузер и свой `localStorage`, общего хранилища нет вообще. Как только появится что угодно общее (сервер, синхронизация между устройствами, совместная работа, любая версия с бэкендом) — это свойство перестаёт быть автоматическим и должно быть спроектировано явно:
- Каждая запись (класс, учитель, расписание и т.д.) должна иметь обязательную привязку к школе (tenant ID) с первого дня схемы данных, а не добавляться потом.
- Ни один запрос на чтение/запись не должен быть физически способен зацепить данные другой школы — проверка принадлежности школе на уровне доступа к данным, а не только в интерфейсе.
- Идентификация школы/пользователя (кто есть кто) — отдельный вопрос, требует решения до появления общего хранилища, не после.

### 9.3 Обязательное тестирование кода
Каждое изменение движка расписания (правила расстановки, дни недели, кабинеты, групповые уроки и т.д.) должно проверяться логическим тестом на конкретном сценарии до публикации — не только проверкой синтаксиса. В текущей разработке это делалось вручную (тестовые сценарии через отдельный запуск кода на моках), но не оформлено в виде постоянного набора тестов в репозитории. На будущее: тестовые сценарии стоит сохранять и накапливать в репозитории, а не терять между сессиями разработки.

## 10. Приватность

При импорте отчёта «Сотрудники» из eMaktab сохраняются только ФИО и колонка «Классы». ПИНФЛ, дата рождения, телефон и электронная почта — **не читаются и не сохраняются** ни в `state`, ни в `localStorage`, ни в экспортируемых файлах.
